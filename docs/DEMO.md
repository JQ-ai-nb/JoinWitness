# 三分钟演示与答辩

1. 跨租户示例：左表 4 笔订单、右表 3 位客户，customer 单键得到 7 行。指出这不是 4×3 全笛卡尔积，而是相同 customer 桶的乘积之和。
2. 点“定位来源”，查看 1 笔订单和 2 位客户。导出三行反例，使用 CLI check 再次复现。删掉其中任何一行，选定的多重匹配问题不再成立。
3. 切换候选键，tenant 加入键后预期 4 行，保留 4、丢失 3、新增 0。所有契约通过后构造来源行对。
4. 第二场景展示 12 与字符串 "12" 不混同、NULL 默认不匹配，以及真正缺失设备。解释这里必须核查完整对表，不能将一个三行片段称作“不存在”的证明。
5. 第三场景前后都是 2 行，但保留 0、丢失 2、新增 2。说明仅比较 count 的迁移回归可能漏掉关联对象全部变化。
6. 展示源码、35 项 MoonBit 测试、SQLite 320 组完整行对对照、三平台四目标 CI 与身份统一检查。

应能独立回答：

- 基数契约为什么只约束 matched groups？它描述当前关联的扩张关系；若还要求全表唯一性，那是不同的数据约束，本版本没有冒充已经验证。
- 为什么 LEFT JOIN 没丢行仍可能违反覆盖率？保留一个 null extension 不代表找到了真实右表记录。
- 三行为什么最小？对所声明的一对多违规，至少需要一侧两条事实和另一侧一条匹配事实；缺少任何一条都不够。
- 反例核验是否防篡改？它检查给定源表中的事实和范围；不证明源表来自谁，也不认证第三方文本说明。
- 如何不枚举匹配积而计算差分？对同一原始行集合，两个匹配谓词的交集就是两套键的合取；按合取键桶计数，再由集合大小相减。
- 候选键更少重复是否一定正确？不一定。必须同时看 lost/gained、覆盖率与业务解释。
- 支持任意 SQL 吗？只支持明确类型的有界等值关联；没有表达式解析、数据库排序规则、隐式转换或非等值关联。
